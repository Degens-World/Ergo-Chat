<Bruno> Regarding multiple assets in the reserve, in addition to what has already been said above about advantages and disadvantages, I would also point to Gresham's law (https://en.wikipedia.org/wiki/Gresham%27s_law) as a disadvantage. If you have two reserve assets and one of them is perceived as "good" (or "better") and the other is perceived as "bad" (or "worse"), there would be a tendency to withdraw the "better" asset from the reserve and leave only the "worse" asset there. Preventing this tendency and protecting against the vulnerabilities that it brings would require a more complex algorithm.

This is the disadvantage that led us to choose a single reserve asset for Djed/SigmaUSD, despite the diversification advantages of multiple reserve assets.

[2023-03-15T13:57:31]
<Bruno> I think an interesting approach to handle multiple reserve assets would be to:

* have multiple deployments of Djed/SigmaUSD, each with a single reserve asset.

* have a new metastablecoin X that is backed by a basket of the other Djed/SigmaUSD stablecoins.

* the weights/ratio of each stablecoin in the basket could be determined by their relative individual TVL. Withdrawals and deposits from the basket could follow a multi-asset liquidity pool approach where the fee increases the more the transaction causes the ratios to deviate from the optimal.

This would guarantee that each Djed/SigmaUSD deployment is simple and free from Gresham's law issues. The new metastablecoin would have the benefit of diversification of reserves, and the multi-asset liquidity pool approach would provide some protection against the issues arising from Gresham's law.

  " A box selector which is parameterized by maximum number of inputs a transaction can have, and optimal number of inputs.
  
   Say, the selector is given boxes denoted by their values (1,2,3,4,...10). Then the selector is working as follows:
  
   1) the selector first picking up boxes in given order (1,2,3,4,...) by using DefaultBoxSelector
   2) if number of inputs exceeds the limit, the selector is sorting remaining boxes(actually, only 10*maximum boxes) by value in descending order and replaces small-value boxes in the inputs by big-value from the tail (1,2,3,4 => 10)
   3) if the number of inputs still exceeds the limit, the selector is trying to throw away the dust if possible. E.g. if inputs are (100, 200, 1, 2, 1000), target value is 1300 and maximum number of inputs is 3, the selector kicks out (1, 2)
   4) if number of inputs after the previous steps is below optimal, the selector is trying to append the dust, by sorting remaining boxes in ascending order and appending them till optimal number of inputs. "

=========
We write sidechain data in a box associated with sidechain id. 

We can make this block spendable every input-block, which would produce a lot of transactions though. So it would be better
to make transaction of class 2 (spendable in ordering block only), and then from a stream of such transactions only one 
included into ordering block is actually included into the blockchain and paying a fee for that, others are not processed
by the network but accounted via Merkle tree included 

Again, sidechain data box is identified via NFT put in the box. The box can be updated via signature corresponding to 
miner's pubkey. In case of a different script, a script may include condition which depends on mining pubkey or 
header votes and always be evaluated to true, e.g. CONTEXT.minerPubKey.size >= 0. 

Register R4 of the box contains hash of sidechain data.

Register R5 of the box contains id of previous box which contains sidechain data, whether included in ordering block, 
or just referenced in input block. 
Refresh transaction is spending box included into last ordering block, and possibly referencing other attempts to spend 
via R5 register of the sidechain data box,

[2025-11-24T10:30:10]
Not exactly. I understand that NiPoPoWs are lightweight proofs used to verify the state of a blockchain without downloading it entirely. But in the context of a Celaut service, the situation works differently.

A Celaut service is, by design, isolated from the network: it’s the hosting node that must provide any external connection. For example, if the service needs to interact with an Ergo node, the hosting node is the one that finds a peer and hands the service an IP and port to connect to. In that setup, the service must trust that the node isn’t lying.

The issue appears when you want to commercialize a service. Imagine a service that takes an ErgoScript and returns potential failure points, and you want to charge one gluon per use. Since any Celaut node can execute that service —because it’s just a self-contained binary— a user could deliberately choose a “controlled” node. When the service inside that node asks for a real connection to the Ergo network, the node could simply simulate the entire network and avoid performing any real transaction. The service would have no way to verify whether the connection is authentic or fully fabricated.

As a result, the service cannot rely on any external interaction that depends on the honesty or fidelity of the node running it. That dependency breaks any pay-per-use model or any mechanism that requires trustworthy verification

"We plan to deploy Matrix gradually:
– First of all, only some mining pools and solo miners will implement Matrix.
They will form peer-to-peer sub-network which peers send input/ordering
blocks related messages to other sub-network peers, but avoid to send them
to other peers (not supporting input blocks yet). At this point extension
fields do not necessarily present in extension section.
– More and more miners support Matrix, and when 90+% hashrate is on it,
lock-in voting takes place. One-epoch indicative voting would be enough. In
case of 90+% hashrate support voting for lock-in, extension fields become
necessary, and so Matrix becomes part of the protocol. However, old block
structure and p2p messages still supported, for bootstrapping nodes with
historical data, and to support older as well as light clients."
